# DeepFlipper protocol v1

Transport: the upstream Expansion Module Protocol (9600 baud discovery, negotiated
460800 baud preferred / 115200 fallback, XOR checksum, <=64 data bytes,
status ACKs, heartbeat <250 ms).
The data stream is varint-length-prefixed `PB.Main`. Our project-local extension
reserves tags **500=request, 501=response**, both `PB_DeepFlipper.Envelope`.
Its field 1 is a JSON string, bounded to 767 UTF-8 bytes. Existing tags stay intact.

ESP32 always discovers at 9600/8N1 using the official expansion_test presence byte
`0xAA` (not a sustained GPIO-low break), waits for a valid heartbeat, then proposes
460800 in the standard little-endian baud frame. It switches its local UART
only after the peer ACK at 9600 and waits 30 ms before starting RPC. A rejected
rate, failed RPC start/hello, or loss of an established connection latches
115200 for subsequent attempts until ESP32 reboot. Missing discovery alone
does not downgrade a fresh module. Failed attempts stop heartbeats and wait
one second before retrying; loss of an established connection also has a
500 ms quiet period before new discovery so the old 250 ms peer watchdog can
close the session. Fallback performs a fresh handshake, never an in-session
speed change or automatic tool replay. `flipper_get_status` includes `uart_baud`
and `uart_fallback`; serial logs also report the negotiated rate. Electrical
stability at the higher rate still requires physical board validation.

Run `python scripts/fetch_dependencies.py`, then `python scripts/sync_protocol.py`.
Canonical sources live here; nanopb output is generated by fbt, never hand-edited.

Each request has `v:1`, `op`, and the connection's `session` (except `hello`).
`hello` creates the connection session; only the UART RPC owner is accepted.

Discovery/baud negotiation/RPC start/hello happen once per connection, not for
each screen update. The Flipper serializes complete TX frames across its RPC and
Expansion threads, including the checksum. ESP32 polls pending module commands
at most every 200 ms, sends UI changes at most every 50 ms (unchanged refresh
2 s), and sends the full public module snapshot on change or every 5 s after
checking once a second. The 100 ms transport heartbeat remains independent.
Fatal frame/ACK/RPC failures stop the transport and restart discovery; diagnostics
retain the last disconnect reason without recording request contents or secrets.
Responses preserve the RPC command ID; JSON has `ok` and an error `code` on failure.
Implemented operations are listed by `capabilities`, never inferred by the model.

`poll` returns at most one acknowledged mailbox command. It is held until the
matching `module.result` arrives; a reset never replays an old session's command.
This handles Flipper settings -> ESP32 without a second RPC client or UART.
`module.result` reports Wi-Fi state, STA/AP IP, setup AP name, recent server
check state and public settings. Saved Wi-Fi passwords and device tokens are
never returned. The initial setup/AP password is an explicit trusted-UART-only
field for local Flipper help; it is not included in model status/tool results.
Reports refresh once per second, allowing the setup help page to show a new IP
without leaving/re-entering the menu.
Tools return a job ID, with `job.get`/`job.cancel` for completion and cancellation.
Do not retry RF/IR output with a new request ID after an uncertain result.

Initial commands: hello, capabilities, status, ui, poll, module.result,
tool.nfc.scan, job.get, job.cancel. UI uses state/emotion/mouth, no chat captions.

## Native RPC multiplexing

The paired firmware's `hello` also returns `native_rpc:1`. ESP32 checks this
before accepting native MCP jobs. The same Expansion stream carries native
System/Storage/App/Desktop/Gui protobufs alongside project tags 500/501. There
is one reader/command owner; no second serial client. Native `PB.Main` messages
are bounded to 4096 bytes, while the JSON envelope stays at 767 bytes. Streaming
`has_next` replies are drained and unsolicited `AppState` (tag 58, command ID 0)
is tracked independently. Short key input batches press/short/release together.
Expansion heartbeats continue during long native app/file operations; companion
status/UI messages are refreshed between commands. The companion watchdog is
10 seconds; physical link loss still closes the Expansion RPC session promptly.

The ESP32 native action engine implements info, paginated directory/apps,
app open/state/RPC exit, short input, audiovisual alert, and bounded saved-file
actions. Saved card/key loads start emulation; they are not general read/write
commands. IR/Sub-GHz actions press, wait, release, exit and verify foreground
release. App startup waits for its asynchronous ready state before file loading.
Only supported launch names or SD FAP paths are accepted; arbitrary arguments,
CLI commands and UART/power-pin manipulation are not exposed. PIN lock denies
mutations and file browsing. Existing foreground apps return busy.

All MCP actions queue bounded jobs on the UART task. Native jobs advertise up
to 30 seconds of server polling. Results distinguish completion, cancellation,
busy, lock, link loss, unknown timeout and unconfirmed stop. Cancellation ACK
only accepts the request; query the final job result for the actual stop state.
Stop failure drops the RPC link so native apps receive session-close cleanup;
it does not claim confirmed hardware stop. Completed records remain available
until queried/reused or a 30-second retention expires. The model must not infer
external target success from `target_state_verified:false`.

## Browser configuration files

ESP32 `/api/identity` exports JSON with `format: "deepflipper.identity"`,
`version: 1`, `device_id` and `client_id`. The authenticated Python admin
`POST /api/connection-profile` accepts those IDs and `server_url`, then exports
`format: "deepflipper.connection"`, version, both IDs, URL, signed device `token`
and `expires_in`. The ESP32 `/api/import` adds its current profile `revision`,
checks both identities and validates every changed field before one NVS commit.
These files do not contain model/server admin credentials; the connection file
is still a device credential and must remain private.

The embedded ESP32 API requires a device web session and CSRF for writes.
`/api/wifi` trials SSID/password together and commits only after a matching-IP
network event; queued acceptance is not connection success. `/api/settings`
handles URL/token/audio/LED with revision checks. `/api/status` separates UART,
association/DHCP, STA/AP IP and recent server hello/auth checks. `/api/test-server`
is a bounded no-audio probe, and speaker/talk tests remain separate actions.

Wi-Fi submission includes a client `request_id`; `/api/status.wifi_trial` keeps
its ID, target SSID, final state/error and before/after commit revisions. This
result survives restoration of an old live network. Credentials are never in the
trial result. The browser can identify an accepted request even if its response
was lost during network handover, and never automatically resubmits the change.
Status also reports profile revision, apply-in-progress, actual app/recording
state and AP close countdown. Voice actions are admitted after configuration is
applied, with explicit prerequisite errors. Connection-profile export includes
`issued_at` and `expires_at` in addition to `expires_in`.

Companion JSON session/command/job identifiers are unsigned 32-bit values. Flipper
seeds sessions from a full-width hardware random value; cJSON `valueint` saturates
above INT32_MAX and must not be used for these IDs. ESP32 validates the numeric
double and preserves all values through UINT32_MAX when echoing the session.
Regression tests cover both signed-boundary halves and exact JSON roundtrips.
Expansion frames are also checked against the actual upstream C encoder/decoder.
