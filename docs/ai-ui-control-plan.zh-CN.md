# 规划：让 AI 像人一样操作 Flipper（看屏幕 + 按键）

状态：**已实现（2026-11-18），待用户 Windows 编译 Flipper + ESP32、重建服务端后真机验证。** 实现说明见 HANDOFF 第 17 节；下文保留为设计依据。

## 1. 现状与问题

现有接口可以分成两类。

**语义接口**：`flipper_nfc_read`、`flipper_run_saved`、`flipper_app_call` 等。

- 用 RPC 模式在后台打开应用，直接拿回结构化结果。
- 优点：快，结果准。
- 缺点：用户在屏幕上看不到过程；只能做 SDK 登记过、或我们单独写过的功能。

**底层输入接口**：`flipper_app_open`、`flipper_press_button`（每次只能按一个键）、`flipper_app_exit`。这些 ESP32 上已经有了，但 AI 实际上用不起来，原因有三个：

1. **看不到屏幕。** 按完键不知道停在哪个页面、选中的是哪一项，只能盲按。
2. **工具说明全是免责话。** 提示词里反复写"仅表示投递事件，不证明页面动作完成"，模型就学会了找借口、不敢操作。
3. **工具调用轮数不够。** 服务端每轮最多 5 次（`connection.chat` 里的 `MAX_DEPTH = 5`）。进一个菜单往往要 5～15 次按键。

截屏只在"人一样操作"这条路上才有用：后台 RPC 动作时屏幕上本来就没什么可看的。
所以截屏应该和按键做成一套，按完键自动把画面读回来，而不是单独提供一个截屏工具。

## 2. 目标效果

用户说："帮我用 Sub-GHz 读一下 433 的遥控器。"

鲸鱼娘：

1. 说"我来操作一下"；
2. Flipper 屏幕上真的打开 Sub-GHz，选中 Read 并进入；
3. 读到信号后读屏，说出协议名，再问"要保存吗？"。

整个过程用户在屏幕上看得到，和人手操作一模一样。
没有接入 SDK 的普通 App 也能用这种方式操作。

## 3. 关键设计：怎样让只认文字的大模型"看懂"屏幕

DeepSeek 是纯文本模型，直接给它 128×64 的位图没有用。方案是两层：

**① 文字层（主力，几乎零成本）**

- **记录**：在 Flipper 的 `canvas_draw_str` 和 `canvas_draw_str_aligned` 里，顺手把本帧画出的每段文字记下来，包括：
  - 坐标；
  - 字体；
  - 当前画笔颜色：白色字说明它画在黑底上，也就是"被选中、反色高亮"的那一项。
- **双缓冲**：`canvas_reset` 时清空本帧记录，`canvas_commit` 时整帧换入，避免读到画到一半的画面。
- **适用范围**：系统菜单、Submenu、VariableItemList、对话框、按钮提示（Back/OK），以及几乎所有用 canvas 画字的第三方 FAP。
- **成本**：主固件约 +0.5 KB Flash（目前余量约 23 KB），RAM 约 1 KB（24 条 × 32 字节）。

**② 位图层（补充）**

- **怎么取**：用固件已有的 RPC 屏幕流取一帧（1024 字节）后立即停流，不改 Flipper 固件。
- **用途**：
  - 管理页面实时显示"屏幕镜像"，好看，也方便调试；
  - 文字层读不到的画面（像素画、波形、图标），可以选配一个视觉模型来看。视觉模型是可选项，默认不开。

AI 拿到的屏幕状态示例：

```json
{"app":"Sub-GHz","screen":[
  {"t":"Read","sel":true},{"t":"Read RAW"},{"t":"Saved"},{"t":"Add Manually"}],
 "hint":["Back"],"changed":true}
```

## 4. 新工具设计（替代现在的单键工具）

| 工具 | 作用 | 位置 |
|---|---|---|
| `flipper_screen` | 读当前前台应用名和屏幕文字（`sel` 表示高亮项）；`bitmap:true` 时额外附带位图 | ESP32 + Flipper 固件 |
| `flipper_press_keys` | 一次最多按 16 个键，例如 `["down","down","ok"]`，可设长按和间隔；**按完自动返回屏幕状态** | ESP32 |
| `flipper_ui_select` | 在当前列表里找到指定文字，自动上下移动直到它被高亮，再按 OK，并核对页面已变化 | ESP32 或服务端组合 |
| `flipper_go_home` | 连按 Back 直到回到主页（有上限次数），返回确认 | ESP32 |
| `flipper_app_open` | 沿用现有实现，打开后自动附带屏幕状态 | 已有，小改 |

有了"按完自动读屏"，免责话就可以删掉：工具结果直接告诉模型现在停在哪个页面，模型自己核对，不需要提示词替它打预防针。

`flipper_ui_select` 和 `flipper_press_keys` 能把 10 多次单键调用压缩成 2～3 次。
同时把服务端的工具调用轮数从 5 提高到 12 左右，操作过程中让鲸鱼娘先说一句"稍等，我在操作"，避免冷场。

## 5. 安全边界（只拦真正不可撤销的一步）

用户说过"不用加各种借口"，所以原则是只拦一处：
**当即将按 OK、且高亮项是发射、写入或删除类按钮时，先口头确认一次**，例如 Send、Transmit、Emulate、Write、Delete、Erase、Format、Brute。

- 确认后再执行。
- 管理页面提供开关，可以关掉这道确认。
- 其他浏览、读取、进出菜单的操作都直接做，不再附加免责话。

## 6. 和现有语义接口的关系

两套接口都保留，由 AI 按需要选：

- **语义接口**：要数据时优先用，比如 NFC 读 UID、解析 Sub-GHz。快、稳，结果是结构化的。
- **UI 操作**：其余情况都用它，包括没有接入 SDK 的应用、用户想看着它操作、或者语义接口不支持的功能。

提示词改成正面说法："能用语义工具就用；否则直接打开应用按键操作，按完读屏核对。"

## 7. 分阶段实施建议

| 阶段 | 内容 | 改动范围 | 工作量 |
|---|---|---|---|
| P1 | 文字层捕获（canvas 钩子 + `rpc_deepflipper.c` 新增 `screen.text`）；ESP32 实现 `flipper_screen` 和 `flipper_press_keys`（按完自动读屏） | Flipper 主固件（约 +0.5 KB）、ESP32 | 中 |
| P2 | `flipper_ui_select`、`flipper_go_home`；服务端调用轮数改为 12，加入操作中的口头反馈；改写提示词，删掉免责话 | ESP32、服务端 | 小～中 |
| P3 | 位图截屏和管理页面"屏幕镜像"；可选视觉模型 | ESP32、服务端 | 中 |
| P4 | 发射／写入／删除前的语音确认及开关；常用 App 的简短操作说明卡（只在用到 UI 工具时注入） | 服务端 | 小 |

每个阶段都需要用户在 Windows 上分别编译 Flipper 和 ESP32 后真机验证。P1 的原生主机测试可以在沙箱里先跑。

## 8. 风险与已知限制

- **不画文字的应用**：用位图画字或纯像素画的游戏、宠物 App 本身，文字层读不到，只能依赖位图加视觉模型。
- **画面持续变化**：动画或计时页面每次读到的结果可能不同，以"按键后稳定 200 ms 再读"为准。
- **锁屏**：PIN 锁屏时不绕过，工具返回 `locked`，由用户解锁。
- **独占扩展串口的应用**：例如 GPIO UART Bridge、手动打开的宠物 App，会暂停 AI 连接，这是现有的资源规则。
- **屏幕流**：位图只取一帧并确认已停流，避免持续占用串口带宽。
